# TPTP-Interpreter

A lexer, parser and interpreter for **TPTP** (Tiny Planar TelePorting), a small language for controlling an imaginary robot that moves around a 2D grid by teleporting. Built in Java with [JavaCC](https://javacc.github.io/javacc/) as coursework for CS259 Formal Languages at the University of Warwick.

Given a TPTP program, the tool:

1. **Validates it.** It reports lexical, syntax and semantic errors with a line number and a readable message.
2. **Analyses it statically.** It classifies each step as *simple* or *non-simple*, depending on whether its arithmetic is positive linear and guaranteed non-negative.
3. **Executes it.** If every step is simple, it runs the program and reports where the robot halts, or detects that it loops forever.

## The language in brief

A program is a list of step instructions followed by a single `run` instruction:

```
dec: if x<3 (x,y) done else (x-3, y+1) and dec;
run dec (10, 0)
```

Each step has the form:

```
STEP: if ID<NUM (ID1, ID2) becomes (E1, E2) and NSTEP else (E3, E4) and ESTEP
```

If the condition holds, the robot teleports from `(ID1, ID2)` to `(E1, E2)` and moves on to `NSTEP`. Otherwise it teleports to `(E3, E4)` and moves on to `ESTEP`. Either `becomes (E1, E2) and` or `(E3, E4) and` can be omitted, in which case the coordinates stay the same. Expressions support `+`, `-`, `*` and parentheses with the usual precedence. When the robot is sent to a step that doesn't exist, it halts.

The example above repeatedly subtracts 3 from `x`, counting the subtractions in `y`, and halts at step `done` with coordinates `(1, 3)`.

## Building and running

Requires Java and JavaCC 7.0.10.

```bash
javacc assignment.jj   # generates TPTP.java and supporting classes
javac *.java
java TPTP < program.txt
```

## Output

For a valid program where every step is simple, the output is either the halting step and final coordinates, or `Loop`:

```
Success
Simple
done 1 3
```

For a valid program with a non-simple step, the output names the first such step:

```
Success
Non-simple
stepName
```

For an invalid program, `Failure` is printed to stdout, and stderr gets the line number and an explanation:

```
2
Step with name 'a1' already exists.
```

## Design

**Single-pass parsing with semantic actions.** Everything happens in JavaCC grammar actions (no JJTree). As each step is parsed, the parser checks the semantic rules: unique step names, no clashes between parameter and step names, distinct parameters, and a condition variable that is one of the step's parameters. It also builds an expression tree for execution.

**Expression trees.** Arithmetic expressions are parsed by a precedence-respecting grammar (`expr → term → factor`) into a small AST (`Num`, `Var`, `BinOp`). Each step keeps its trees in a `StepData` record, which the interpreter evaluates.

**Simplicity analysis.** Linearity is computed bottom-up during parsing. Any multiplication, or any subtraction whose right operand isn't a plain numeral, makes an expression non-linear, and subtraction is rejected outright in the "true" branch. For the "false" branch, `isNonNegative` uses the fact that the condition `ID<NUM` being false implies `ID ≥ NUM` to check that the new coordinates can never go negative.

**Error reporting.** JavaCC's `ParseException` and `TokenMgrError` are caught and translated into friendlier messages, such as `Unexpected token ';', expected an identifier`. Semantic violations throw a custom `TPTPException` that carries the line number.

**Loop detection.** The interpreter records every visited configuration `(step, x, y)` and reports `Loop` if one repeats. Some programs visit too many points to store them all. To handle those, once the number of stored configurations reaches 100 × the number of steps, it switches to tracking configurations modulo 10. This targets the case where every update is either a constant or `v ± c` with `c ≤ 9`. It is a heuristic designed for that case rather than a general decision procedure.
